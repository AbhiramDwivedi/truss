2. **A retro that finds every problem, generically.** Works on any project, not just counting truss events. It
   identifies problems, ranks them by wall-clock and token cost, and proposes fixes and optimizations:
   - Time: where crew wall-clock went (agent work, slot/lock/admission waits, test runs, QC rounds, rework,
     conflict resumes, idle gaps, waits on the client, API outages).
   - Code structure: churn hotspots, files that conflict at merge, file size, coupling between crews' owns; propose
     splits/refactors as project goals.
   - Tests: suite duration trend, flaky tests (fail then pass on the same head), tests run vs needed.
   - Quality loop: why rounds repeat; QC findings that were wrong or too strict.
   - Rules and gates: refusals, owns-check stops, out-of-owns edits, whether the rule or the crew was wrong.
   - Cost: tokens and $ per crew and role, spawns per role, model mix.
   - Each finding: evidence (counted, never guessed), cost, proposed fix, target (plugin, project config, or project
     code as a goal for the client). Product-code findings become proposed goals, never auto-fixes.
   **Open-ended (client ruling 2026-11-13):** that list is a starting checklist, not the scope. The retro agent's
   brief says plainly it is empowered, and expected, to find any other problem or optimization the evidence shows,
   reported in the same format, never dropped for fitting no category; it may name new categories. A test pins the
   wording, and judge/triage keep findings outside the known categories. It reads the structured events 0.31.0
   records (step timings, test durations, slot waits, conflicts), not transcripts, and finishes in bounded time.
3. **Memory consolidation ("dreaming").** Between waves, a step consolidates docs/knowledge and the architecture
   notes: merges duplicates, resolves contradictions, prunes entries the code no longer supports, re-points
   citations by symbol. It proposes a diff a reviewer checks; it never deletes silently.
4. **Planning flags hotspots.** The design engineer's plan and the checking engineer flag a file most planned crews
   will touch, and propose a refactor goal first or one crew owning it, instead of scheduling serial merges.
5. **Bounded proactivity.** When a wave ends, the PM proposes the next goals from retro findings with evidence and a
   cost estimate; it never starts them unasked.
