### Admission and reap folds in stage.js (R-142, 0.32.0)

A member start costs no separate admit or reap runner call where a factory call sits next to it. `redStep` sets `crew.admitPlan` (`planAdmit`) for the first member the crew will start, the UX direction when the crew has one to take, else the planner, and `runFactory` adds `--admit-first <slug> --admit-label <label> --admit-title <title>` (with `--admit-persona` and `--admit-high` for a member that has them) before `--dir`, and before heavy's `--`, on the red check. The answer's `admittedFirst` object waits in `crew.admitFirst`, and `admit` takes it (`takeAdmitFirst`, only for the same label, title, persona and high) instead of calling the runner; any other runner call voids it. A held `admittedFirst` is judged as a held admit is (`held by admission:`, `BLOCKED: budget:`, `BLOCKED: awaiting client:`). A crew with saved tasks, or a start no factory call precedes, keeps the standalone admit. In `bin/factory/admit.ts` (called by the `factory.ts` dispatcher), `takeAdmitFlag` lifts the `--admit-*` flags off the line, only before a `--`, and `admitFirst` runs `cmdAdmit` with them after any `--reap-first` reap and before the command; the body, a refusal's too, rides on the output as `admittedFirst`. That folded admission has no `--wait-ms`, so a memory hold on it stops the crew at once, where the standalone `admit --wait-ms 90000` re-checks for up to 90 s. The crew-end reap rides on the late-reply read in `runCrew` (`--reap-first`, as every member's reap does) and runs alone (`reap`) only when it is still due after that read, which is when no factory call follows.

`cmdAdmit` in `bin/factory/admit.ts` reaps too. Before it judges admission it runs `cmdReap` for the crew's `<slug>-check` label, which stops and removes every recorded group whose `heavyPid` is dead and skips one whose heavy job still runs. The body carries `reaped` (the pgids), or `reapError` when the reap threw; neither changes the verdict, and a refusal carries them as well. So a direct crew, which the program manager runs with one `admit` per member start (`skills/run/SKILL.md`, "Direct crews"), needs no `reap` call of its own. The proof is the `tests/heavy-slots-032.check.ts` case "a direct crew's member start runs admission and the reap inside the same factory call".

## Heavy job on win32 and the run limit (0.32.0)

This section corrects "Heavy slots" and "Background heavy jobs" above: a lock whose owner pid is dead is no longer the only stale lock, and a heavy job is no longer left to run for ever.

On win32 the background heavy job works without negative-pid signals. `heavyMain(argv, sys?)` and `heavyJobMain(argv, sys?)` take `sys = { platform, spawn }` (type `HeavySys`), defaulting to `process.platform` and `child_process.spawn`. `heavyMain` uses only `sys.spawn`, which it hands to `startJob`. `heavyJobMain` uses both and passes the platform to `acquireSlot`, on to `takeHeavySlot`, and to `releaseHeavySlot`. The wrapper and its command spawn with `windowsHide: true`. A group is its leader's pid: `groupAlive` checks the pid, and `killGroup` runs the tree kill `taskkill /pid <pid> /T /F` through `treeKill` (the wrapper runs it through `sys.spawn`). `cmdReap` takes the platform, so it reaps a recorded group the same way. The win32 branches are proven by a stubbed platform and spawn layer in `tests/heavy-slots-032.check.ts`, because there is no Windows host; they have not run on Windows.

A hung job no longer holds its slot for ever. The wrapper stops the command's group once it has run for `TRUSS_HEAVY_RUN_MS` (default `slotWaitMs(dir)`, `runMsOf` in `bin/factory/slot.ts`): SIGTERM, SIGKILL after 2 s, the tree kill on win32. It then releases the slot and writes `result.json` with `timedOut: true`, and `heavyMain` prints `heavy.timedOut: true`. It does not record that run in `heavy-times.jsonl`, so a hang never stretches the next wait. As a second line of defence, `acquireSlot` writes `until` into the slot's `owner.json`: the take time plus the run limit plus `HEAVY_GRACE_MS` (15 s). `takeSlot` in `resources/index.ts` treats a lock past `until` as stale even while its owner pid lives. It stops the holder first, by the groups under `resources/groups` whose `heavyPid` is the owner pid and then the owner pid, and takes the lock through the existing `takeOver`, so only one waiter removes it. A lock with no `until` (written by an older plugin) behaves as before. Which jobs count as heavy does not change, and `factory check` still takes the slot itself only for a full suite; its slot gets the same `until`.

A process id can be reused while a hung holder's lock waits past `until`, so the takeover could signal an unrelated process that now has the owner's pid. The window is the grace plus the time until the next waiter, and the lock's token is re-read just before the kill.
