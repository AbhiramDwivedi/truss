## Heavy job on win32 and the run limit (0.32.0)

This section corrects "Heavy slots" and "Background heavy jobs" above: a lock whose owner pid is dead is no longer the only stale lock, and a heavy job is no longer left to run for ever. It also corrects the "A stuck heavy lock" paragraph of "Failure modes and recovery": a waiter takes over a lock past its `until` deadline even while its owner lives, and stops the holder and the holder's groups first.

On win32 the background heavy job works without negative-pid signals. `heavyMain(argv, sys?)` and `heavyJobMain(argv, sys?)` take `sys = { platform, spawn }` (type `HeavySys`), defaulting to `process.platform` and `child_process.spawn`. `heavyMain` uses only `sys.spawn`, which it hands to `startJob`. `heavyJobMain` uses both and passes the platform to `acquireSlot`, on to `takeHeavySlot`, and to `releaseHeavySlot`. The wrapper and its command spawn with `windowsHide: true`. A group is its leader's pid: `groupAlive` checks the pid, and `killGroup` runs the tree kill through `treeKill`, and the wrapper stops its command through `killGroup`. `cmdReap` takes the platform, so it reaps a recorded group the same way. The win32 branches are proven by a stubbed platform and spawn layer in `tests/heavy-slots-032.check.ts`, because there is no Windows host; they have not run on Windows.

A hung job no longer holds its slot for ever. The wrapper stops the command's group once it has run for `TRUSS_HEAVY_RUN_MS` (a `factory check` job, which takes the slot inside its own command, gets the wait limit on top, because its slot wait runs on the same timer) (default `slotWaitMs(dir)`, `runMsOf` in `bin/factory/slot.ts`): SIGTERM, SIGKILL after 2 s, the tree kill on win32. It then releases the slot and writes `result.json` with `timedOut: true`, and `heavyMain` prints `heavy.timedOut: true`. A slot job records that run in `heavy-times.jsonl` with `timedOut: true`, and so does a check job (`slot: false`, no wrapper token) whose run the limit stopped, or whose check a waiting crew's `until` takeover killed by signal after the run limit (`heavyJobMain` counts that signal death as the limit, so the caller sees `timedOut` too): `slotWaitMs` skips the row, so a hang never stretches the next wait, while `runMsOf` raises the next default limit to twice the longest such run (never above `HEAVY_WAIT_MAX_MS`), so a healthy suite longer than the default limit is stopped once and not for ever. As a second line of defence, `acquireSlot` writes `until` into the slot's `owner.json`: the take time plus the run limit plus `HEAVY_GRACE_MS` (15 s). `takeSlot` in `resources/index.ts` treats a lock past `until` as stale even while its owner pid lives. It stops the holder first (`stopHolder`), by the groups under `resources/groups` whose `heavyPid` or `pgid` is the owner pid, then the owner's own process group when it leads one, then the owner pid, and takes the lock through the existing `takeOver`, so only one waiter removes it. A direct `factory check` suite runs as its own process group with a record under `resources/groups` (`heavyPid` is the check's pid; `bashRun` in `bin/factory/check.ts`), so that takeover stops the suite too. Under `factory heavy` the check leads the group the wrapper spawned and runs its suite inside it, the wrapper's record names that group by its `pgid`, and `bashRun` writes no record of its own (`TRUSS_HEAVY_JOB`), so the takeover's group stop ends the suite too. A lock with no `until` (written by an older plugin) behaves as before. Which jobs count as heavy does not change, and `factory check` still takes the slot itself only for a full suite; its slot gets the same `until`.

A process id can be reused while a hung holder's lock waits past `until`, so the takeover could signal an unrelated process that now has the owner's pid. The window is the grace plus the time until the next waiter, and the lock's token is re-read just before the kill.

A limit past what `setTimeout` can hold (2147483647 ms, about 24.8 days) is clamped in `heavyJobMain`, since Node would otherwise run any longer delay after 1 ms and stop the command at once.

A goalCheck is such a job, and the limit stops it with SIGTERM to its group. The internal `goal-check-job` (`goalCheckJobMain`, `cmdGoalCheckJob` in `bin/factory/decide.ts`) therefore runs the check async with a SIGTERM handler, so it outlives the check's death, removes the worktree, prunes, deletes the temp dir and appends one decision line (`stopped by the run limit (exit <n>)`). Its body then carries `timedOut: true`, and `goalCheckMain` passes `timedOut: true` with `ok: false` to the PM even when the job left only a tail. The PM should read `timedOut` as a limit stop, not a red target, and raise `TRUSS_HEAVY_RUN_MS` before starting a fix crew.

Whether Claude Code's TaskStop reaches a detached heavy job is deferred: it needs a live Claude Code session, which no crew member has, so no evidence exists yet. The run limit does not depend on the answer.

### Admission and reap folds in stage.js (R-142, 0.32.0)

A member start costs no separate admit or reap runner call where a factory call sits next to it. `redStep` sets `crew.admitPlan` (`planAdmit`) for the first member the crew will start, the UX direction when the crew has one to take, else the planner, and `runFactory` adds `--admit-first <slug> --admit-label <label> --admit-title <title>` (with `--admit-persona` and `--admit-high` for a member that has them) before `--dir`, and before heavy's `--`, on the red check. The answer's `admittedFirst` object waits in `crew.admitFirst`, and `admit` takes it (`takeAdmitFirst`, only for the same label, title, persona and high) instead of calling the runner; any other runner call voids it. A held `admittedFirst` is judged as a held admit is (`held by admission:`, `BLOCKED: budget:`, `BLOCKED: awaiting client:`). A crew with saved tasks, or a start no factory call precedes, keeps the standalone admit. In `bin/factory/admit.ts` (called by the `factory.ts` dispatcher), `takeAdmitFlag` lifts the `--admit-*` flags off the line, only before a `--`, and `admitFirst` runs `cmdAdmit` with them after any `--reap-first` reap and before the command; the body, a refusal's too, rides on the output as `admittedFirst`. That folded admission has no `--wait-ms`, so `runFactory` stores it with `noWait: true`, and `admit` in `workflows-src/stage/crew.js` treats a hold that carries admit's own figures (`minFreeMB`) as a memory or parallelism hold and runs the standalone `admit --wait-ms 90000` re-check, as ADR-0046 item 1 says for a gates admit. A budget or awaiting hold still stops the crew at once. The crew-end reap rides on the late-reply read in `runCrew` (`--reap-first`, as every member's reap does) and runs alone (`reap`) only when it is still due after that read, which is when no factory call follows.

`cmdAdmit` in `bin/factory/admit.ts` reaps too. Before it judges admission it runs `cmdReap` for the crew's `<slug>-check` label, which stops and removes every recorded group whose `heavyPid` is dead and skips one whose heavy job still runs. The body carries `reaped` (the pgids), or `reapError` when the reap threw; neither changes the verdict, and a refusal carries them as well. So a direct crew, which the program manager runs with one `admit` per member start (`skills/run/SKILL.md`, "Direct crews"), needs no `reap` call of its own. The proof is the `tests/heavy-slots-032.check.ts` case "a direct crew's member start runs admission and the reap inside the same factory call".

## Fragment heading depth (stitch)

`fragmentSections` in `bin/fragments.ts` takes the shallowest heading depth in a fragment as the section depth. Text before the first heading of that depth is preamble: `stitchDoc` drops it and warns `text before the first heading is ignored`. So a fragment starts with its shallowest heading, and a deeper section placed first is lost. Put a `###` section under a `##` section that comes first. A fragment cannot replace a `###` section of the doc and a `##` section in one file: the `###` is then part of the `##` section above it.
