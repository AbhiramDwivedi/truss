## Heavy job on win32 and the run limit (0.32.0)

This section corrects "Heavy slots" and "Background heavy jobs" above: a lock whose owner pid is dead is no longer the only stale lock, and a heavy job is no longer left to run for ever.

On win32 the background heavy job works without negative-pid signals. `heavyMain(argv, sys?)` and `heavyJobMain(argv, sys?)` take `sys = { platform, spawn }` (type `HeavySys`), defaulting to `process.platform` and `child_process.spawn`. `heavyMain` uses only `sys.spawn`, which it hands to `startJob`. `heavyJobMain` uses both and passes the platform to `acquireSlot`, on to `takeHeavySlot`, and to `releaseHeavySlot`. The wrapper and its command spawn with `windowsHide: true`. A group is its leader's pid: `groupAlive` checks the pid, and `killGroup` runs the tree kill through `treeKill`, and the wrapper stops its command through `killGroup`. `cmdReap` takes the platform, so it reaps a recorded group the same way. The win32 branches are proven by a stubbed platform and spawn layer in `tests/heavy-slots-032.check.ts`, because there is no Windows host; they have not run on Windows.

A hung job no longer holds its slot for ever. The wrapper stops the command's group once it has run for `TRUSS_HEAVY_RUN_MS` (a `factory check` job, which takes the slot inside its own command, gets the wait limit on top, because its slot wait runs on the same timer) (default `slotWaitMs(dir)`, `runMsOf` in `bin/factory/slot.ts`): SIGTERM, SIGKILL after 2 s, the tree kill on win32. It then releases the slot and writes `result.json` with `timedOut: true`, and `heavyMain` prints `heavy.timedOut: true`. A slot job records that run in `heavy-times.jsonl` with `timedOut: true`: `slotWaitMs` skips the row, so a hang never stretches the next wait, while `runMsOf` raises the next default limit to twice the longest such run (never above `HEAVY_WAIT_MAX_MS`), so a healthy suite longer than the default limit is stopped once and not for ever. As a second line of defence, `acquireSlot` writes `until` into the slot's `owner.json`: the take time plus the run limit plus `HEAVY_GRACE_MS` (15 s). `takeSlot` in `resources/index.ts` treats a lock past `until` as stale even while its owner pid lives. It stops the holder first (`stopHolder`), by the groups under `resources/groups` whose `heavyPid` or `pgid` is the owner pid, then the owner's own process group when it leads one, then the owner pid, and takes the lock through the existing `takeOver`, so only one waiter removes it. A direct `factory check` suite runs as its own process group with a record under `resources/groups` (`heavyPid` is the check's pid; `bashRun` in `bin/factory/check.ts`), so that takeover stops the suite too. Under `factory heavy` the check leads the group the wrapper spawned and runs its suite inside it, the wrapper's record names that group by its `pgid`, and `bashRun` writes no record of its own (`TRUSS_HEAVY_JOB`), so the takeover's group stop ends the suite too. A lock with no `until` (written by an older plugin) behaves as before. Which jobs count as heavy does not change, and `factory check` still takes the slot itself only for a full suite; its slot gets the same `until`.

A process id can be reused while a hung holder's lock waits past `until`, so the takeover could signal an unrelated process that now has the owner's pid. The window is the grace plus the time until the next waiter, and the lock's token is re-read just before the kill.

Whether Claude Code's TaskStop reaches a detached heavy job is deferred: it needs a live Claude Code session, which no crew member has, so no evidence exists yet. The run limit does not depend on the answer.

### Admission and reap folds in stage.js (R-142, 0.32.0)

A member start costs no separate admit or reap runner call where a factory call sits next to it. `redStep` sets `crew.admitPlan` (`planAdmit`) for the first member the crew will start, the UX direction when the crew has one to take, else the planner, and `runFactory` adds `--admit-first <slug> --admit-label <label> --admit-title <title>` (with `--admit-persona` and `--admit-high` for a member that has them) before `--dir`, and before heavy's `--`, on the red check. The answer's `admittedFirst` object waits in `crew.admitFirst`, and `admit` takes it (`takeAdmitFirst`, only for the same label, title, persona and high) instead of calling the runner; any other runner call voids it. A held `admittedFirst` is judged as a held admit is (`held by admission:`, `BLOCKED: budget:`, `BLOCKED: awaiting client:`). A crew with saved tasks, or a start no factory call precedes, keeps the standalone admit. In `bin/factory/admit.ts` (called by the `factory.ts` dispatcher), `takeAdmitFlag` lifts the `--admit-*` flags off the line, only before a `--`, and `admitFirst` runs `cmdAdmit` with them after any `--reap-first` reap and before the command; the body, a refusal's too, rides on the output as `admittedFirst`. That folded admission has no `--wait-ms`, so `runFactory` stores it with `noWait: true`, and `admit` in `workflows-src/stage/crew.js` treats a hold that carries admit's own figures (`minFreeMB`) as a memory or parallelism hold and runs the standalone `admit --wait-ms 90000` re-check, as ADR-0046 item 1 says for a gates admit. A budget or awaiting hold still stops the crew at once. The crew-end reap rides on the late-reply read in `runCrew` (`--reap-first`, as every member's reap does) and runs alone (`reap`) only when it is still due after that read, which is when no factory call follows.

`cmdAdmit` in `bin/factory/admit.ts` reaps too. Before it judges admission it runs `cmdReap` for the crew's `<slug>-check` label, which stops and removes every recorded group whose `heavyPid` is dead and skips one whose heavy job still runs. The body carries `reaped` (the pgids), or `reapError` when the reap threw; neither changes the verdict, and a refusal carries them as well. So a direct crew, which the program manager runs with one `admit` per member start (`skills/run/SKILL.md`, "Direct crews"), needs no `reap` call of its own. The proof is the `tests/heavy-slots-032.check.ts` case "a direct crew's member start runs admission and the reap inside the same factory call".

## Failure modes and recovery

**A stalled agent.** The heartbeat prompts the PM. The PM messages the stalled agent's project manager, or the project manager itself, and asks for its state. `/truss` keeps showing the agent as stalled until it does something. Before stopping it, the PM or project manager reads its transcript tail: a resumed agent may be compacting.

**An idle project manager.** A project manager seen to go idle without a final report in its stint, while no member works, gets one `[truss] idle project manager:` prompt after 15 minutes. The PM resumes it with a message, or starts its successor from its report.

**The usage limit.** When the five-hour window runs out while crews work, the limit-reset wake prompts the PM after the reset. The PM messages each project manager that hasn't sent its final report: "Usage limit reset. Resume from where you stopped."

**A project manager stops with work left.** Its report starts with `CHECKPOINT:`. The PM starts a fresh project manager, `<slug>-2` (then `-3`), from that report. The successor's brief names the original goal file, the predecessor's branch and commit, and the crew's original base commit; the successor resets its worktree to the predecessor's branch first. Its members, QC engineers and report folder carry its own name. The other project managers are told the new name. A member that stops with `CHECKPOINT:` is handled the same way inside the crew: a fresh member from its handoff note, never a resume.

**A project manager tries to stop without a report.** The stop gate sends it back, at most twice in a row. After that the stop goes through, and the PM sees a report that isn't in the fixed format.

**A lost hand-back.** Hand-backs from nested agents have been lost on some machines. The report is on disk anyway: the project manager reads `reports/<crew>/<member>.md`, and the PM reads `reports/<project-manager>/<project-manager>.md`, at the path in the `[truss]` note from the Agent call.

**A QC engineer FAIL.** The project manager sends the findings to a builder. Each later QC engineer is a fresh agent under the next unused name, never a resume, and any fix after a FAIL or a stress-test break needs a fresh QC engineer. When two fix attempts at one level end with the same check failing, the project manager climbs the ladder: Sonnet, then Opus at `medium`, `high`, `xhigh`, each step a fresh agent whose first deliverable is a root-cause analysis with evidence. When `xhigh` fails twice, the project manager sends `BLOCKED:` with the failing check, its output and the theories ruled out, and the PM takes it to the client. In `single` mode an integration-qc FAIL goes back to the integrator, and a fresh `integration-qc-2` rules next.

On a v2 plan, the QC engineer FAILs a crew may repair are bounded. Once a crew's this-run FAIL count is greater than `reworkAllowance`, the hooks refuse its next QC engineer, and the project manager sends the allowance-blocked message to `main` with the last findings. A spent allowance goes to the PM, never up an effort level. The PM takes it to the client, or re-plans; a successor project manager starts a fresh count ([ADR-0004](adr/0004-scope-repair-and-head-gates.md), section 5).

**A verdict on the wrong commit.** The PM merges only when the QC file's `## Proof checked` SHA equals `git rev-parse <crew branch>`. After a merge of the target that moved the head, the old PASS doesn't count. The SHA is the QC engineer's head line, and a PASS also stands for a moved head when the patch line equals the merged branch's `PATCH_COMMAND` id, with `<base>` the target head last merged in, and the project manager's checks passed again after the merge. The project manager stop gate enforces the same rule as a send-back ([ADR-0004](adr/0004-scope-repair-and-head-gates.md), section 6).

**A start held by admission** ([ADR-0015](adr/0015-resource-aware.md), proposed). `start` lists the crew under `held` and leaves it `planned`; a member held inside a stage stops its crew `BLOCKED` with text `held by admission: ...`. The PM starts `truss:resource-monitor`, writes `resources/parallelism.json` if it lowers the parallelism, and re-runs `start` or resumes the crew with `start --slug <s> --resume answers` once memory recovers.

**A stuck heavy lock** (ADR-0015, proposed). A waiter takes over a lock whose owner pid is dead, one whose `owner.json` `until` deadline has passed even while its owner lives (it stops the holder and the holder's groups first, [ADR-0054](adr/0054-heavy-slot-run-limit.md)), or one with no `owner.json` older than 3 s (`OWNERLESS_MS`, `bin/store.ts`). When no `heavy` runs and a lock still blocks, delete `resources/heavy.lock/` in the truss dir by hand.

**A reload mid-session.** The module's memory starts over. An agent that ended before the reload resolves to no crew, so a message to it from a crew agent is refused. A pending limit-reset wake survives in plugin state.
