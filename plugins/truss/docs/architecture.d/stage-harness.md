### Stage step tests (0.32.0, R-140)

A stage test can drive one step without the whole bundle. `bin/build-stage.ts` `loadStageStep(file, stubs)` reads one `workflows-src/stage/` module, drops its `// stage.js module:` line and its `export` keywords, and runs the body as an AsyncFunction whose parameters are the stub names (`agent`, `args`, `log`, runner-side calls such as `integrate`). It returns `{ loaded, scope }`, where `scope` holds the module's top-level functions, consts, lets and classes. A free name that is neither declared by the module nor stubbed throws a ReferenceError when reached, so a single-step test shows what its step really needs. A file outside `STAGE_SRC_DIR` or without the module comment is refused. `loadStageBundle(stubs)` does the same for the committed `workflows/stage.js`, with `meta` not exported and the top-level run (`const results = await Promise.all(F.crews.map(runCrew))` and what follows) cut off; it throws when that line is not found. When `stubs.args` has no `truss`, the bundle loader gives it `{ dir: '/', repo: '/' }`, because the bundle's load-time code needs an `args.truss` object and reads its `dir`.

`bin/testmap.ts` follows this: a test that names one step module by a relative literal reaches that module only. A test that calls `loadStageBundle` reaches the generated `stage.js` (`stageBundles`) and so every module, as a test that names `stage.js` does. This supersedes the "each module selects every stage test" remark in the 0.31.0 text above for tests written single-step; existing stage tests still run the bundle, so their counts do not drop.
