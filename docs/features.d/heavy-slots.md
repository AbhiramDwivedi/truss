## Background heavy jobs (0.31.0)

- What: `factory heavy` starts a detached `factory heavy-job` wrapper that owns the slot for exactly the command's lifetime and releases it when the command exits, so a runner Bash call killed at 600 s no longer frees a slot while its suite still runs. The caller waits up to 540 s (`HEAVY_ATTACH_MS`, env `TRUSS_HEAVY_ATTACH_MS`), then prints `{heavy: {pending: true, ageMs, budgetMs}}` with exit 1; running the same line again attaches to the same job. The budget is the slot wait plus `slotWaitMs` for the run. `stage.js` `check()` re-runs a pending line until the job's age reaches that budget (`pendingOutOfBudget`), then stops the crew BLOCKED with `heavy run still going after N s (budget M s)`. The spawner records the wrapper pid when it starts it (`startJob`, `jobAlive`), so a slow-starting wrapper is never started twice. The wrapper takes no slot for `factory check`, which takes it itself only for a full suite (`suiteRun`), including an acceptance test that is only `npm test`.
- Since 0.32.0 the job works on win32 and a hung command never holds its slot for ever. `heavyMain` and `heavyJobMain` take `sys = { platform, spawn }` (defaults `process.platform` and `child_process.spawn`); on win32 every spawn uses `windowsHide: true` and a group kill is the tree kill `taskkill /pid <pid> /T /F` through `sys.spawn`, with no negative-pid signal (`groupAlive`, `killGroup` and `treeKill` in `resources/index.ts` take the platform; `cmdReap` takes it too). A command still running after `TRUSS_HEAVY_RUN_MS` (default `slotWaitMs(dir)`, `runMsOf` in `bin/factory/slot.ts`) has its group stopped (SIGTERM, then SIGKILL 2 s later), the slot released and `result.json` written with `timedOut: true`; `heavyMain` prints `heavy.timedOut: true`. A run the limit stopped is not recorded as a suite time. Each slot's `owner.json` also carries `until` (start plus the run limit plus `HEAVY_GRACE_MS`, 15 s); `takeSlot` treats a lock past `until` as stale even while its pid lives, stops the holder (the groups under `resources/groups` whose `heavyPid` is the owner pid, then the owner pid) and takes the lock through `takeOver`. The win32 path has run only under a stubbed platform and spawn layer, never on Windows.
- Entry points: `plugins/truss/bin/factory/heavy.ts` (`heavyMain`, `heavyJobMain`, `jobKey`, `startJob`, `jobAlive`), `plugins/truss/bin/factory/slot.ts` (`acquireSlot`, `runMsOf`, `slotWaitMs`, `recordHeavyTime`), `plugins/truss/bin/factory/reap.ts` (`cmdReap`), `plugins/truss/resources/index.ts` (`takeHeavySlot`, `killGroup`, `treeKill`), `plugins/truss/workflows/stage.js` (`check`, `pendingOf`, `pendingOutOfBudget`); tests `plugins/truss/tests/heavy-031.check.ts`, `plugins/truss/tests/heavy-slots-032.check.ts`, `plugins/truss/tests/stage-tests-031.check.ts`.
- Owner: `truss-plugin-node` (factory.ts), `truss-workflow-scripts` (stage.js).
- Docs: [architecture](../plugins/truss/docs/architecture.md) ("Background heavy jobs", "Heavy job on win32 and the run limit (0.32.0)").
