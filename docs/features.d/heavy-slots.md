## Fewer runner spawns (reap fold, same-head skip)

- What: the reap after each member spawn rides on the crew's next factory call as `--reap-first <slug>`; `factory.ts` reaps `<slug>-check` before running the command and adds `reapedFirst: {error}` to its output only when that reap failed. The crew-end reap rides on the late-reply read, the crew's last factory call, and runs as a runner call of its own only when a reap is still due and no call follows (`runCrew`). Green, owns-check and the tests check skip a re-run while the crew head has not moved since they passed. A stubbed crew with a stress fix went from 32 runner spawns to 24 (26 since ADR-0046 item 8 adds the regression tester's admit and integrate).
- What (0.29.0, gates): the checks before QC (green, owns-check, tests check, knowledge lint, QC admit) go out as one runner call, `factory gates --slug S --steps ...`, which runs the due steps in order, stops at the first unmet one and prints each step's own output under `steps` with `gates`, `codes` and `stopped`. stage.js takes each step's result from that call and falls back to the single command when it has none. The same stubbed crew now costs 22 runner spawns; a real crew saves about 4 at the end of its member chain and about 3 per QC fix round.
- What (0.32.0, R-142): the red check, the factory call just before the crew's first member start (the UX direction, else the planner), carries that member's admission as `--admit-first <slug> --admit-label <label> --admit-title <title>` (plus `--admit-persona` and `--admit-high` when the member has them), placed before `--dir` and before heavy's `--`. `admit()` takes its answer from the call's `admittedFirst` and makes no runner call; a held `admittedFirst` stops the crew as a held admit does (`held by admission:`, `BLOCKED: budget:`, `BLOCKED: awaiting client:`). A crew that resumes with saved tasks, or a member start that no factory call precedes, keeps the standalone admit. The admission inside `--admit-first` (`admitFirst`) runs with no memory wait; when it comes back held with admit's own figures (`minFreeMB`), `admit` in `crew.js` runs the standalone `admit --wait-ms 90000` re-check, and a budget or awaiting hold stops the crew at once. Every `admit` (`cmdAdmit`), standalone or folded, first reaps the crew's `<slug>-check` groups whose heavy job has exited and adds `reaped` (or `reapError`, which never changes the verdict) to its body, so a direct crew's member start is one `admit` call with no separate `reap`. The crew-end reap of `runCrew` rides on the late-reply read and runs alone only when `crew.reapDue` is still set after it.

## Background heavy jobs (0.31.0)

- What: `factory heavy` starts a detached `factory heavy-job` wrapper that owns the slot for exactly the command's lifetime and releases it when the command exits, so a runner Bash call killed at 600 s no longer frees a slot while its suite still runs. The caller waits up to 540 s (`HEAVY_ATTACH_MS`, env `TRUSS_HEAVY_ATTACH_MS`), then prints `{heavy: {pending: true, ageMs, budgetMs}}` with exit 1; running the same line again attaches to the same job. The budget is the slot wait plus `slotWaitMs` for the run. `stage.js` `check()` re-runs a pending line until the job's age reaches that budget (`pendingOutOfBudget`), then stops the crew BLOCKED with `heavy run still going after N s (budget M s)`. The spawner records the wrapper pid when it starts it (`startJob`, `jobAlive`), so a slow-starting wrapper is never started twice. A slot job writes a `held` file in its job dir once it has the slot, and a caller whose attach budget ran out waits up to 10 s more (`SETTLE_MS`) for it, so a pending result on a loaded host means the job holds the slot or is queued for it. The wrapper takes no slot for `factory check`, which takes it itself only for a full suite (`suiteRun`), including an acceptance test that is only `npm test`.
- Since 0.32.0 the job works on win32 and a hung command never holds its slot for ever. `heavyMain` and `heavyJobMain` take `sys = { platform, spawn }` (defaults `process.platform` and `child_process.spawn`; `heavyMain` uses only `sys.spawn`); on win32 every spawn uses `windowsHide: true` and a group kill is the tree kill in `killGroup` and `treeKill`, with no negative-pid signal (`groupAlive`, `killGroup` and `treeKill` in `resources/index.ts` take the platform; `cmdReap` takes it too). A command still running after `TRUSS_HEAVY_RUN_MS` (default `slotWaitMs(dir)`, `runMsOf` in `bin/factory/slot.ts`) has its group stopped (SIGTERM, then SIGKILL 2 s later), the slot released and `result.json` written with `timedOut: true`; `heavyMain` prints `heavy.timedOut: true`. A run the limit stopped is recorded with `timedOut: true`: it is no suite time for `slotWaitMs`, but `runMsOf` raises the next default limit to twice the longest of them, so a healthy long suite is not stopped for ever. Each slot's `owner.json` also carries `until` (start plus the run limit plus `HEAVY_GRACE_MS`, 15 s); `takeSlot` treats a lock past `until` as stale even while its pid lives, stops the holder (`stopHolder`: the groups under `resources/groups` whose `heavyPid` or `pgid` is the owner pid, the owner's own group, then the owner pid) and takes the lock through `takeOver`. The win32 path has run only under a stubbed platform and spawn layer, never on Windows.
